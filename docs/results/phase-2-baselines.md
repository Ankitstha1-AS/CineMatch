# Phase 2 — Baselines on the validation split

Evaluation of the five models specified in `AGENTS.md` section 4 (M0–M4) on the
per-user temporal validation split. The test split has **not** been touched; it
is reserved for the single final evaluation after the hybrid is tuned.

Generated by `python -m ml.pipeline.evaluate --config ml/config.yaml`. Raw
metrics, hyper-parameters, fit times and dataset hashes are stored in
[`ml-25m-subset-validation.json`](ml-25m-subset-validation.json).

## Protocol

| Item | Value |
|---|---|
| Dataset | `ml-25m-subset` (1,478,848 ratings, 9,960 users, 8,737 movies) |
| Fit | `train` — 1,068,184 ratings |
| Evaluate | `validation` — 118,785 ratings |
| Split | Per-user temporal hold-out ([manifest](../splits/ml-25m-subset.json)) |
| Ranking candidates | Every catalogue movie the user did not rate in training |
| Relevance | Validation rating >= 4.0 |
| Ranking users | 9,137 users with at least one relevant validation item |

## Observations

- **M4 is the strongest rating predictor** (RMSE 0.8460, MAE 0.6410). Latent
  factors capture user/item interactions that biases alone cannot, which is the
  expected reason the hybrid uses M4 for the collaborative rating component.
- **M3 is the strongest ranker by a wide margin** (NDCG@10 0.0609 vs 0.028 for
  the next best). Its item neighbours are also the natural source of
  collaborative explanations in Phase 3.
- **M1 is a surprisingly strong ranking baseline** for its cost, but it shows
  only 0.6% catalogue coverage at K = 10: it recommends the same head items to
  everyone. M3 reaches 19.8%.
- **M2 has by far the widest coverage** (51.2% at K = 10) and the highest
  novelty, confirming that content features reach the long tail. Its ranking
  quality is low on its own, which is exactly the gap the hybrid must close.
- **M0 is a rating lower bound only**: using its predicted rating as a ranking
  score performs poorly, as expected.

These results give the hybrid (M5) a clear target: combine M2's coverage and
interpretability with M3/M4's ranking accuracy, using the adaptive weight to
protect users with few ratings.

## Notes on M3

Raw cosine item-KNN ranked almost randomly on this sparse subset (~113 ratings
per movie). Two standard corrections fixed it:

- **Significance weighting** — a similarity is scaled by
  `n_common / (n_common + 10)`, where `n_common` is the number of users who
  rated both movies, so one co-rating cannot create a strong neighbour.
- **Shrinkage** — predictions are pulled towards the user mean with
  `(sum sim * rating + 5 * mean) / (sum |sim| + 5)`, so items supported by a
  single neighbour do not receive extreme scores.

## Reproduce

```bash
python -m ml.pipeline.split --config ml/config.yaml      # once
python -m ml.pipeline.evaluate --config ml/config.yaml   # validation
cd ml && python -m pytest                                 # 31 tests
```

A quick development run that samples 200 ranking users:

```bash
python -m ml.pipeline.evaluate --config ml/config.yaml --max-users 200 \
  --out docs/results/ml-25m-subset-validation-quick.json
```
